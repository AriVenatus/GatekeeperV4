# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Gatekeeper is a Python/discord.py Discord bot that integrates with CubeCoders AMP (a game-server control panel) over AMP's JSON/POST HTTP API. It lets Discord users manage AMP-hosted game servers (console access, chat bridging, whitelist sync, banners, etc.) from Discord. This repo (`GatekeeperV4`, `AriVenatus/GatekeeperV4`) is a fork of `leonbreidenbach-pc/GatekeeperV3`, itself a fork of the original `k8thekat/GatekeeperV2` — it's under active development (no longer maintenance-only), see `README.md`'s "Why use this fork?" section for the fork deltas so far.

## Commands

- **Run**: `python start.py` from the repo root. Requires a `.env` file (copy `.env.template` and fill it in) or the same variables exported as real environment variables — see `core/AMP_Handler.py::val_settings()`.
  - Useful flags (full list in `docs/INSTALL.md` "Launch Args"): `-dev` (dev-mode logging), `-super` (skip downgrading the bot's AMP account from Super Admin), `-whitelist-only` (restrict the bot's own AMP role to the minimum needed for whitelist sync), `-debug`, `-discord` (disable Discord connection, useful for testing AMP/DB in isolation).
  - On startup, `start.py` runs `pip install -r requirements.txt` automatically (skipped if `requirements.txt`'s hash hasn't changed since the last install — see `Setup.pip_install()`).
- **Lint**: `ruff check .` (config in `pyproject.toml` under `[tool.ruff]`; not pinned in `requirements.txt`, install separately if needed).
- **Type-check**: `pyright` (config in `pyproject.toml` under `[tool.pyright]`, basic mode).
- **Tests**: there is no test suite in this repo.

## Architecture

### Startup sequence
`start.py` (`Setup.__init__`) parses CLI args, runs the conditional `pip install`, initializes logging (`core/logger.py`), opens the SQLite DB (`DB.getDBHandler()`), then starts `AMP_Handler.AMP_init` in a background thread and blocks until `AMP_Handler.AMP_setup` is `True` before launching the Discord client (`discordBot.client_run`). The AMP thread keeps polling for instance changes every 30s via `AMP_Handler.amp_server_instance_check()` for the life of the process.

### AMP integration layer
- `core/AMP_Handler.py` — process-wide singleton (`AMP_Handler.getAMPHandler()` / global `Handler`). Loads secrets (`val_settings()`, via `_load_tokens_from_env()`: env vars / a `.env` file), dynamically discovers per-game-type API modules from `modules/*/amp_*.py` (`moduleHandler()`, keyed by each module's `DisplayImageSources` list), and discovers/tracks live AMP instances as `AMP.AMPInstance` objects (`_instanceValidation()`).
- `core/AMP.py` — `AMPInstance` is the base wrapper around AMP's API (`CallAPI`, login/session handling). One instance represents the main AMP install (`InstanceID == 0`) and one per game server. On init it ensures the bot's own AMP account has a `Gatekeeper` role with the right permission nodes (`setup_AMPbotrole` / `setup_Gatekeeper_Permissions`), pulling the node list from `core/amp_permissions.py` (`perms_super()` for full access, `perms_whitelist_only()` for the minimal whitelist-sync-only footprint, selected via the `-whitelist-only` flag). `self.perms` (used to *check* current permissions) is derived from the same profile function as what's actually granted — keep these in sync if you touch either.
- `modules/<Game>/amp_<game>.py` — per-game subclasses of `AMPInstance` (e.g. `AMPMinecraft`) implementing game-specific AMP API calls (whitelist add/remove via console commands, etc.), each with its own `self.perms` permission list and `setup_Gatekeeper_Permissions()` override, independent from the main-instance profile above. `modules/Generic/` is the fallback used when no game-specific module matches.

#### `-whitelist-only` needs live verification before production use
On every startup and every 30s poll, Gatekeeper calls the AMP API `ADSModule/GetInstances` (`AMPInstance.getInstances()`) to discover instances — for both permission profiles. It's undocumented whether this endpoint requires an explicit `ADS.*` permission node, and `perms_whitelist_only()` deliberately grants none. If it turns out `GetInstances` does need one, the bot loses the ability to see any AMP instance after the first restart with `-whitelist-only`.
- **How to test**: start the bot with `-whitelist-only` using a fresh bot account that still has `Super Admins`; let it restart (this is when Super Admin gets removed and the narrowed `Gatekeeper` role/permissions get applied); check the log for `***ATTENTION*** Please ensure the permissions are set correctly, the Bot cannot find any AMP Instances at this time...`; confirm a Minecraft whitelist add/remove still works end-to-end via Discord-Role sync.
- **Expected result**: no "cannot find any AMP Instances" message, and whitelist sync still functions.
- **If it fails**: add an `ADS.*` (or a narrower `ADS.InstanceManagement.*` read-only) node to `perms_whitelist_only()` in `core/amp_permissions.py` and re-test.

### Discord bot layer
- `core/discordBot.py` — the `discord.py` `commands.Bot` subclass (`Gatekeeper`). `setup_hook()` delegates to `loader.Handler`.
- `core/loader.py` — dynamically loads two kinds of extensions at startup: (1) `module_auto_loader()` loads `modules/<Game>/cog_<game>.py` files whose `DisplayImageSources` match a currently-connected AMP instance (plus `modules/Generic/generic.py` always); (2) `cog_auto_loader()` loads every file in `cogs/` as a discord.py extension, resolving load order via each cog's module-level `Dependencies = [...]` list (cogs with unmet dependencies are retried until the list is empty). `permissions_cog.py` is excluded from auto-load and loaded on-demand instead.
- `cogs/*.py` — the core (non-game-specific) command surface: `amp_server_cog`, `amp_tasks_cog`, `db_server_cog`, `db_user_cog`, `permissions_cog`, `banner_cog`, `regex_cog`, `whitelist_cog` (manual whitelist requests), `whitelist_sync_cog` (Discord-Role↔Whitelist sync). See `docs/COMMANDS.md` for the full command reference and `docs/WHITELIST.md`/`docs/PERMISSIONS.md`/`docs/BANNER.md`/`docs/REGEX.md` for feature-specific docs.
- **Per-lookup-type commands need subcommands, not an enum param**: `db_user_cog.py`'s `/user info` used to be one command with an `identifier_type` Choice (`Discord`/`Minecraft`/`Steam`) plus two always-visible optional params (`identifier`, `user`) — confusing, since Discord slash commands **cannot conditionally show/hide a parameter based on another parameter's chosen value**, so both fields showed regardless of which type was picked, and `identifier` was redundant with `user` for the Discord case anyway. Now it's `/user info discord|minecraft|steam`, each exposing only its one relevant (required) param, sharing DB-lookup/embed logic via a private `_send_user_info()` helper. General lesson for any future per-type-lookup command: if which parameter is relevant depends on another parameter's value, split into subcommands — there is no supported single-command way to do that in Discord's slash-command UI. The three-subcommand list Discord shows while typing `/user info` (one row per subcommand) is expected rendering, not a regression — every other multi-subcommand group in this bot (`/link minecraft`/`steam`/`show`/`remove`, `/server settings ...`, etc.) looks the same.
- **Escape external/API-sourced text before interpolating it into embed markdown**: `/link steam` and `/link minecraft` build their confirmation embeds by dropping the Steam personaname / Minecraft IGN straight into markdown (a clickable `[name](url)` link, and `**bold**` text respectively) via `i18n.t(...)`. Neither is escaped, so a display name containing a markdown special character (an `_` is common in both Steam and Minecraft names) gets partially misrendered as emphasis instead of showing literally. Fixed by wrapping the name in `discord.utils.escape_markdown(...)` before interpolating — the Steam link stays fully clickable, only the *display text* is escaped. General lesson: any user/API-controlled string (not just these two) headed into an f-string or `i18n.t(...)` call that also contains deliberate markdown syntax should go through `discord.utils.escape_markdown()` first, or a rogue `_`/`*`/`` ` ``/`~` in someone's display name will bleed into the surrounding formatting. Also note: real backtick/code-block formatting and an active Discord link are mutually exclusive — backticks suppress all markdown parsing inside them, including link syntax — so "code-styled but still clickable" isn't achievable at all.

### Internationalization (i18n)
Gatekeeper supports English (default) and German as a single **global** language, switchable by an admin at runtime — not per-user Discord client locale. `core/i18n.py` (singleton, `i18n.getI18nHandler()`, mirrors `AMP_Handler.getAMPHandler()`/`DB.getDBHandler()`) loads `locales/en.json`/`locales/de.json` (flat `"dotted.key": "text"` maps, no nesting) and exposes `i18n.t(key, **kwargs)` (looked up, `.format(**kwargs)`'d, falls back EN → raw key on a miss, never raises) and `i18n.t_plural(key_base, count, **kwargs)` (picks `.one`/`.other`). Current language is cached on the handler and persisted via the existing generic `DBConfig` setting `'Language'` (`'en'`/`'de'` strings, deliberately not ints — numeric-string `DBConfig` values get auto-coerced to `int` on read, see `core/DB.py`'s `DBConfig.__getattribute__`).

- **Command metadata** (`commands.<qualified_name with spaces→dots>.description` / `...params.<name>.description` / `...params.<name>.choices.<choice.value>`) uses a key scheme mechanically derived from each command's own `qualified_name`, so the same key is both hand-written at decoration time and re-derivable later with no separate mapping table. Non-command strings are hand-namespaced: `common.*` (shared across ≥2 files, verified by grep before merging — not blindly deduped), `messages.<area>.*`, `embeds.<function>.*`, `ui.<component>.*`.
- **Startup**: `core/discordBot.py` calls `i18n.getI18nHandler()` immediately after `import DB` (before `Gatekeeper.setup_hook()` triggers `loader.Handler`'s cog imports), since command decorators call `i18n.t(...)` at each cog's module-import time — this is what makes cold-start rendering correct in whichever language was last persisted.
- **Live switch**: `/bot language` (admin-only, `@commands.has_guild_permissions(administrator=True)` — same tier as `/bot moderator`/`/bot permissions`, stricter than the general `@utils.role_check()` most `/bot` subcommands use, since this is a global setting affecting every user at once) calls `i18n.set_language(...)` then `i18n.retranslate_command_tree(client)`, which walks `client.tree.walk_commands()` **and** `client.walk_commands()` (the whole surface is hybrid commands, so both trees need walking — the app-command tree Discord's UI reads, and the prefix-command tree `$help` reads) and mutates each already-registered `Command`/`Group`'s `.description`, each param's `.description` (via the private `Command._params` dict — `to_dict()` reads it fresh, confirmed by reading discord.py 2.4.0's actual source; **re-verify this still exists/is-mutable before any discord.py version bump**, per the existing caution below), and each `Choice.name` (never `.value` — those are compared in business logic, e.g. `if permission.value == 0`, and must stay stable across a language switch). A length guard skips (logs + keeps old text) any translated string outside Discord's 1–100 char limit, since one oversized field would otherwise fail the entire bulk `tree.sync()`. Only *after* this does `core/discordBot.py` call the normal `tree.copy_global_to()` + `tree.sync()`. Message bodies (`context.send(i18n.t(...))`) need no such resync — they're evaluated fresh on every invocation and just read whatever language is currently active.
- **Coverage**: `core/discordBot.py`, `core/utils.py`, `core/utils_embeds.py`, `core/utils_ui.py`, `utils_dev/banner_editor/*` (the actually-live banner editor UI — `core/utils_ui.py` has a parallel `Banner_Editor_View`/etc. that is **dead code**, never imported outside itself; don't waste time translating it further, translate `utils_dev/banner_editor/` instead), and all of `cogs/*.py` except `amp_tasks_cog.py`. Deliberately **not** translated: `amp_tasks_cog.py`'s console/chat/event webhook relay (raw AMP/game text, not authored UI copy — also its webhook display names are a stored identity key matched by exact string equality across restarts, so translating them would orphan/duplicate webhooks), and admin-authored custom whitelist-reply templates stored in the DB (`DB.GetAllWhitelistReplies()` — user content, not source strings). `modules/*/cog_<game>.py` currently register zero commands (pure boilerplate) so there was nothing to translate there — if a future game module gains real slash commands, they need the same `i18n.t()` treatment as `cogs/*.py`.
- Translating text surfaced a few real (non-translation) bugs, fixed in the same pass: `context.sned(...)` typo in `core/discordBot.py`; `amp_server_cog.py`'s `/server status` referenced `amp_server.InstanceName` on a variable just checked `== None`; `core/utils_ui.py`'s `ServerButton` derived its AMP permission node (`server.start`/`.stop`/etc., checked against `bot_perms.json`) from the *display label* — translating "Start" to "Starten" would have silently broken that permission check, now decoupled via an explicit `action` param.
- **Full text-quality audit (2026-08-09)**: beyond translation coverage, did a line-by-line pass over all 457 keys in both `locales/en.json` and `locales/de.json` checking grammar/accuracy, not just presence. Recurring bug classes found and fixed: missing English possessive apostrophes (`a Users...` → `a User's...`), an anglicism verb wrongly inflected as English past tense instead of German (`Synced` → `Synchronisiert`), missing hyphens in German compounds (`Gatekeeper Neustart-Funktion` → `Gatekeeper-Neustart-Funktion`), a wrong German noun gender/case (`das Server-Avatar` → `den Server-Avatar` — `Avatar` is masculine), an untranslated phrase left mid-German-sentence (`Server Console` → `Server-Konsole`), comma splices rewritten in both languages, and a couple of plain typos/formatting slips (`seperator`, a missing space before a parenthesis, a wrong preposition). None of this is caught by length/key-parity validation alone (see the length-guard note above) — worth an occasional manual read-through, not just automated checks, especially after adding a batch of new keys.
- **German naturalness pass (2026-08-09)**: the 2026-08-09 audit above checked grammar/accuracy; this pass instead targeted *phrasing that reads as a stiff, calque-y translation* even though each sentence was individually grammatical — flagged by a user screenshot of `/bot bannergroup remove`'s confirmation ending mid-sentence ("Sieht so aus, als hätten wir gerade entfernt"). Two classes of fix:
  1. **Systemic phrasing**: German has ~20 messages translating English's "Looks like X" via `"Es sieht so aus, als [Konjunktiv II]..."` — grammatically valid but reads as hedging/uncertain in German (unlike the casual-idiomatic English source) and gets clunkier the longer the sentence. Replaced with the idiomatic patterns already used correctly elsewhere in the same file: `anscheinend`/`scheint … zu` instead of the full subordinate clause. Same principle applied to a few sibling English-source constructs where a direct statement read more naturally than a hedge paired with an exclamation mark (e.g. `messages.banner.settings.type.images`).
  2. **Composition bugs** (the actual root causes, not just wording): (a) `and_part` in `cogs/banner_cog.py`'s three banner-group message builders was hardcoded to the **English literal** `' and '` regardless of active language — a stray English word bleeding into German sentences; moved to a new shared key `common.and_joiner` (`" and "` EN / `" und "` DE) added to both locale files. (b) `/bot bannergroup remove` had no `need_selection` guard (unlike `/bot bannergroup add`, which has one) — calling it with neither `server` nor `channel` silently "succeeded" with all three interpolated parts empty, which is exactly the screenshot's cause; added the missing guard (new key `messages.banner.group.remove.need_selection`, mirroring `add`'s). (c) `messages.bot.utils.message_timeout.result`'s German fragments composed into a broken sentence — `{content_str}` (`"wird nach {time} Sekunden gelöscht"`) plus the wrapper's own trailing `" nach dem Senden."` produced a duplicated `"... nach {time} Sekunden gelöscht nach dem Senden."`, and `wird` didn't agree in number with the plural `Ephemere Nachrichten`; moved `"nach dem Senden"` fully into the two `content_str` variants (now `werden …`) and simplified the wrapper to just `"{content_str}."`. (d) `messages.whitelist_request.need_ign_reason` is only ever consumed as a lowercase mid-sentence fragment of `cannot_handle` (`"Ich kann deine Anfrage nicht bearbeiten, {reason}"`), but was itself a full capitalized sentence (`"Ich brauche deinen **IGN**, ..."`) — produced a mid-sentence capital "Ich" and a redundant repeated clause; rewritten as a proper lowercase fragment (`"mir fehlt noch dein **IGN**."`). General lesson: whenever a locale string is built by interpolating one `i18n.t(...)` result into another (`content_str`, `reason`, `and_part`, etc.), check the *composed* sentence, not each fragment in isolation — grammar/casing/agreement bugs only show up in the concatenation, and a hardcoded literal in the composing Python code silently defeats localization even when both JSON files are correct.
- **Raw internal state must never go through i18n, even when a matching key already exists (2026-08-14)**: `core/utils_embeds.py`'s `_bool_str()` (shared by `server_info_embed`/`server_display_embed`/`server_status_embed`/`bot_settings_embed`) rendered `True`/`False` via `i18n.t('common.bool.true'/'false')`, so a German-language bot literally printed "Wahr"/"Falsch" for internal DB boolean fields (Donator-only, Whitelist-open, Hidden, Console-Filtered, ...) in embeds — flagged by a user screenshot. Fixed by having `_bool_str()` return the fixed literal `` `True`/`False` `` directly (backtick-wrapped, no i18n lookup at all). **The `common.bool.true`/`common.bool.false` keys themselves were left translated on purpose** — they're legitimately reused elsewhere as Discord Choice-dropdown labels (`/server console filter`, `/bot utils sync`, `/server settings donator`, etc.), where showing the active language is correct UI copy. General lesson: the same locale key can be correct in one call site and wrong in another — a boolean/enum reflecting raw internal state should never route through `i18n.t()`, even if a conveniently-named key already exists, so check every *use site* of a shared key rather than assuming a single fix (or a single "should this be translated" judgment) applies everywhere it's referenced. Same pass also caught an unrelated plain code bug hiding behind the same call: `server_info_embed` rendered `Console_Filtered_Type` (0=Blacklist/1=Whitelist, not a bool at all) through this same `_bool_str()`, showing `True`/`False` instead of `Blacklist`/`Whitelist` — fixed with a dedicated `_filter_type_str()` helper and two new `embeds.common.filter_type.*` keys.

### Database layer
`core/DB.py` wraps a single SQLite DB (`Database` class). Model classes `DBServer`, `DBUser`, `DBBanner`, `DBConfig` override `__setattr__` so a plain `some_db_obj.Field = value` in application code immediately persists to SQLite (via `Database._UpdateServer`/`_UpdateBanner`/`_UpdateUser`, each guarded by a per-table column allowlist) — there's no separate "save"/"commit" call. Schema is created fresh in `Database._InitializeDatabase`; existing databases are migrated incrementally by versioned methods in `core/DB_Update.py`, gated on `DB_Version`.

### Logging
`core/logger.py` configures the standard `logging` module plus two custom levels via `haggis.logs.add_logging_level`: `DEV` (15, between DEBUG/INFO; enabled by `-dev`) and `COMMAND` (19; enabled by `-command`, used to log every slash-command invocation). Get the shared logger anywhere with `logging.getLogger()` (no name arg — it's the root logger).

### Secrets
Environment variables / a `.env` file (copy `.env.template`, gitignored), loaded by `AMP_Handler.AMPHandler._load_tokens_from_env()` via `python-dotenv`. Ends up as `AMPHandler.tokens`, read throughout the codebase as `self.AMPHandler.tokens.<Field>` (e.g. `AMPUser`, `AMPPassword`, `AMPurl`, `AMPAuth`, `SteamAPIKey`, `token`). There used to be a second, `tokens.py`-file-based path (checked first, `.env` as fallback) — removed in favor of `.env`-only, since it's what every real deployment (see the deployment log) already used.
