# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Gatekeeper is a Python/discord.py Discord bot that integrates with CubeCoders AMP (a game-server control panel) over AMP's JSON/POST HTTP API. It lets Discord users manage AMP-hosted game servers (console access, chat bridging, whitelist sync, banners, etc.) from Discord. This repo (`GatekeeperV3.1`, `AriVenatus/GatekeeperV3.1`) is a fork of `leonbreidenbach-pc/GatekeeperV3`, itself a fork of the original `k8thekat/GatekeeperV2` — it's in **maintenance mode**, not active feature development, aside from the specific fork deltas listed in `README.md`'s "Why use this fork?" section.

## Commands

- **Run**: `python start.py` from the repo root. Requires either `tokens.py` (copy `tokenstemplate.py` and fill it in) or a `.env`/environment variables based on `.env.template` — see `AMP_Handler.py::val_settings()`.
  - Useful flags (full list in `README.md` "Launch Args"): `-dev` (dev-mode logging, uses `tokens_dev.py` if present), `-super` (skip downgrading the bot's AMP account from Super Admin), `-whitelist-only` (restrict the bot's own AMP role to the minimum needed for whitelist sync), `-debug`, `-discord` (disable Discord connection, useful for testing AMP/DB in isolation).
  - On startup, `start.py` runs `pip install -r requirements.txt` automatically (skipped if `requirements.txt`'s hash hasn't changed since the last install — see `Setup.pip_install()`).
- **Lint**: `ruff check .` (config in `pyproject.toml` under `[tool.ruff]`; not pinned in `requirements.txt`, install separately if needed).
- **Type-check**: `pyright` (config in `pyproject.toml` under `[tool.pyright]`, basic mode).
- **Tests**: there is no test suite in this repo.

## Architecture

### Startup sequence
`start.py` (`Setup.__init__`) parses CLI args, runs the conditional `pip install`, initializes logging (`logger.py`), opens the SQLite DB (`DB.getDBHandler()`), then starts `AMP_Handler.AMP_init` in a background thread and blocks until `AMP_Handler.AMP_setup` is `True` before launching the Discord client (`discordBot.client_run`). The AMP thread keeps polling for instance changes every 30s via `AMP_Handler.amp_server_instance_check()` for the life of the process.

### AMP integration layer
- `AMP_Handler.py` — process-wide singleton (`AMP_Handler.getAMPHandler()` / global `Handler`). Loads secrets (`val_settings()`: tries `tokens.py`/`tokens_dev.py` first, falls back to env vars/`.env` via `_load_tokens_from_env()`), dynamically discovers per-game-type API modules from `modules/*/amp_*.py` (`moduleHandler()`, keyed by each module's `DisplayImageSources` list), and discovers/tracks live AMP instances as `AMP.AMPInstance` objects (`_instanceValidation()`).
- `AMP.py` — `AMPInstance` is the base wrapper around AMP's API (`CallAPI`, login/session handling). One instance represents the main AMP install (`InstanceID == 0`) and one per game server. On init it ensures the bot's own AMP account has a `Gatekeeper` role with the right permission nodes (`setup_AMPbotrole` / `setup_Gatekeeper_Permissions`), pulling the node list from `amp_permissions.py` (`perms_super()` for full access, `perms_whitelist_only()` for the minimal whitelist-sync-only footprint, selected via the `-whitelist-only` flag). `self.perms` (used to *check* current permissions) is derived from the same profile function as what's actually granted — keep these in sync if you touch either.
- `modules/<Game>/amp_<game>.py` — per-game subclasses of `AMPInstance` (e.g. `AMPMinecraft`) implementing game-specific AMP API calls (whitelist add/remove via console commands, etc.), each with its own `self.perms` permission list and `setup_Gatekeeper_Permissions()` override, independent from the main-instance profile above. `modules/Generic/` is the fallback used when no game-specific module matches.

#### `-whitelist-only` needs live verification before production use
On every startup and every 30s poll, Gatekeeper calls the AMP API `ADSModule/GetInstances` (`AMPInstance.getInstances()`) to discover instances — for both permission profiles. It's undocumented whether this endpoint requires an explicit `ADS.*` permission node, and `perms_whitelist_only()` deliberately grants none. If it turns out `GetInstances` does need one, the bot loses the ability to see any AMP instance after the first restart with `-whitelist-only`.
- **How to test**: start the bot with `-whitelist-only` using a fresh bot account that still has `Super Admins`; let it restart (this is when Super Admin gets removed and the narrowed `Gatekeeper` role/permissions get applied); check the log for `***ATTENTION*** Please ensure the permissions are set correctly, the Bot cannot find any AMP Instances at this time...`; confirm a Minecraft whitelist add/remove still works end-to-end via Discord-Role sync.
- **Expected result**: no "cannot find any AMP Instances" message, and whitelist sync still functions.
- **If it fails**: add an `ADS.*` (or a narrower `ADS.InstanceManagement.*` read-only) node to `perms_whitelist_only()` in `amp_permissions.py` and re-test.

### Discord bot layer
- `discordBot.py` — the `discord.py` `commands.Bot` subclass (`Gatekeeper`). `setup_hook()` delegates to `loader.Handler`.
- `loader.py` — dynamically loads two kinds of extensions at startup: (1) `module_auto_loader()` loads `modules/<Game>/cog_<game>.py` files whose `DisplayImageSources` match a currently-connected AMP instance (plus `modules/Generic/generic.py` always); (2) `cog_auto_loader()` loads every file in `cogs/` as a discord.py extension, resolving load order via each cog's module-level `Dependencies = [...]` list (cogs with unmet dependencies are retried until the list is empty). `Permissions_cog.py` is excluded from auto-load and loaded on-demand instead.
- `cogs/*.py` — the core (non-game-specific) command surface: `AMP_server_cog`, `AMP_tasks_cog`, `DB_server_cog`, `DB_user_cog`, `Permissions_cog`, `banner_cog`, `regex_cog`, `whitelist_cog` (manual whitelist requests), `whitelist_sync_cog` (Discord-Role↔Whitelist sync). See `COMMANDS.md` for the full command reference and `WHITELIST.md`/`PERMISSIONS.md`/`BANNER.md`/`REGEX.md` for feature-specific docs.
- **Per-lookup-type commands need subcommands, not an enum param**: `DB_user_cog.py`'s `/user info` used to be one command with an `identifier_type` Choice (`Discord`/`Minecraft`/`Steam`) plus two always-visible optional params (`identifier`, `user`) — confusing, since Discord slash commands **cannot conditionally show/hide a parameter based on another parameter's chosen value**, so both fields showed regardless of which type was picked, and `identifier` was redundant with `user` for the Discord case anyway. Now it's `/user info discord|minecraft|steam`, each exposing only its one relevant (required) param, sharing DB-lookup/embed logic via a private `_send_user_info()` helper. General lesson for any future per-type-lookup command: if which parameter is relevant depends on another parameter's value, split into subcommands — there is no supported single-command way to do that in Discord's slash-command UI.

### Internationalization (i18n)
Gatekeeper supports English (default) and German as a single **global** language, switchable by an admin at runtime — not per-user Discord client locale. `i18n.py` (singleton, `i18n.getI18nHandler()`, mirrors `AMP_Handler.getAMPHandler()`/`DB.getDBHandler()`) loads `locales/en.json`/`locales/de.json` (flat `"dotted.key": "text"` maps, no nesting) and exposes `i18n.t(key, **kwargs)` (looked up, `.format(**kwargs)`'d, falls back EN → raw key on a miss, never raises) and `i18n.t_plural(key_base, count, **kwargs)` (picks `.one`/`.other`). Current language is cached on the handler and persisted via the existing generic `DBConfig` setting `'Language'` (`'en'`/`'de'` strings, deliberately not ints — numeric-string `DBConfig` values get auto-coerced to `int` on read, see `DB.py`'s `DBConfig.__getattribute__`).

- **Command metadata** (`commands.<qualified_name with spaces→dots>.description` / `...params.<name>.description` / `...params.<name>.choices.<choice.value>`) uses a key scheme mechanically derived from each command's own `qualified_name`, so the same key is both hand-written at decoration time and re-derivable later with no separate mapping table. Non-command strings are hand-namespaced: `common.*` (shared across ≥2 files, verified by grep before merging — not blindly deduped), `messages.<area>.*`, `embeds.<function>.*`, `ui.<component>.*`.
- **Startup**: `discordBot.py` calls `i18n.getI18nHandler()` immediately after `import DB` (before `Gatekeeper.setup_hook()` triggers `loader.Handler`'s cog imports), since command decorators call `i18n.t(...)` at each cog's module-import time — this is what makes cold-start rendering correct in whichever language was last persisted.
- **Live switch**: `/bot language` (admin-only, `@commands.has_guild_permissions(administrator=True)` — same tier as `/bot moderator`/`/bot permissions`, stricter than the general `@utils.role_check()` most `/bot` subcommands use, since this is a global setting affecting every user at once) calls `i18n.set_language(...)` then `i18n.retranslate_command_tree(client)`, which walks `client.tree.walk_commands()` **and** `client.walk_commands()` (the whole surface is hybrid commands, so both trees need walking — the app-command tree Discord's UI reads, and the prefix-command tree `$help` reads) and mutates each already-registered `Command`/`Group`'s `.description`, each param's `.description` (via the private `Command._params` dict — `to_dict()` reads it fresh, confirmed by reading discord.py 2.4.0's actual source; **re-verify this still exists/is-mutable before any discord.py version bump**, per the existing caution below), and each `Choice.name` (never `.value` — those are compared in business logic, e.g. `if permission.value == 0`, and must stay stable across a language switch). A length guard skips (logs + keeps old text) any translated string outside Discord's 1–100 char limit, since one oversized field would otherwise fail the entire bulk `tree.sync()`. Only *after* this does `discordBot.py` call the normal `tree.copy_global_to()` + `tree.sync()`. Message bodies (`context.send(i18n.t(...))`) need no such resync — they're evaluated fresh on every invocation and just read whatever language is currently active.
- **Coverage**: `discordBot.py`, `utils.py`, `utils_embeds.py`, `utils_ui.py`, `utils_dev/banner_editor/*` (the actually-live banner editor UI — `utils_ui.py` has a parallel `Banner_Editor_View`/etc. that is **dead code**, never imported outside itself; don't waste time translating it further, translate `utils_dev/banner_editor/` instead), and all of `cogs/*.py` except `AMP_tasks_cog.py`. Deliberately **not** translated: `AMP_tasks_cog.py`'s console/chat/event webhook relay (raw AMP/game text, not authored UI copy — also its webhook display names are a stored identity key matched by exact string equality across restarts, so translating them would orphan/duplicate webhooks), and admin-authored custom whitelist-reply templates stored in the DB (`DB.GetAllWhitelistReplies()` — user content, not source strings). `modules/*/cog_<game>.py` currently register zero commands (pure boilerplate) so there was nothing to translate there — if a future game module gains real slash commands, they need the same `i18n.t()` treatment as `cogs/*.py`.
- Translating text surfaced a few real (non-translation) bugs, fixed in the same pass: `context.sned(...)` typo in `discordBot.py`; `AMP_server_cog.py`'s `/server status` referenced `amp_server.InstanceName` on a variable just checked `== None`; `utils_ui.py`'s `ServerButton` derived its AMP permission node (`server.start`/`.stop`/etc., checked against `bot_perms.json`) from the *display label* — translating "Start" to "Starten" would have silently broken that permission check, now decoupled via an explicit `action` param.
- **Full text-quality audit (2026-08-09)**: beyond translation coverage, did a line-by-line pass over all 457 keys in both `locales/en.json` and `locales/de.json` checking grammar/accuracy, not just presence. Recurring bug classes found and fixed: missing English possessive apostrophes (`a Users...` → `a User's...`), an anglicism verb wrongly inflected as English past tense instead of German (`Synced` → `Synchronisiert`), missing hyphens in German compounds (`Gatekeeper Neustart-Funktion` → `Gatekeeper-Neustart-Funktion`), a wrong German noun gender/case (`das Server-Avatar` → `den Server-Avatar` — `Avatar` is masculine), an untranslated phrase left mid-German-sentence (`Server Console` → `Server-Konsole`), comma splices rewritten in both languages, and a couple of plain typos/formatting slips (`seperator`, a missing space before a parenthesis, a wrong preposition). None of this is caught by length/key-parity validation alone (see the length-guard note above) — worth an occasional manual read-through, not just automated checks, especially after adding a batch of new keys.

### Database layer
`DB.py` wraps a single SQLite DB (`Database` class). Model classes `DBServer`, `DBUser`, `DBBanner`, `DBConfig` override `__setattr__` so a plain `some_db_obj.Field = value` in application code immediately persists to SQLite (via `Database._UpdateServer`/`_UpdateBanner`/`_UpdateUser`, each guarded by a per-table column allowlist) — there's no separate "save"/"commit" call. Schema is created fresh in `Database._InitializeDatabase`; existing databases are migrated incrementally by versioned methods in `DB_Update.py`, gated on `DB_Version`.

### Logging
`logger.py` configures the standard `logging` module plus two custom levels via `haggis.logs.add_logging_level`: `DEV` (15, between DEBUG/INFO; enabled by `-dev`) and `COMMAND` (19; enabled by `-command`, used to log every slash-command invocation). Get the shared logger anywhere with `logging.getLogger()` (no name arg — it's the root logger).

### Secrets
Primary: `tokens.py` (gitignored, copy from `tokenstemplate.py`) or `tokens_dev.py` when `-dev` is set. Fallback when neither exists: environment variables / a `.env` file (see `.env.template`), loaded by `AMP_Handler.AMPHandler._load_tokens_from_env()` via `python-dotenv`. Either path ends up as `AMPHandler.tokens`, read throughout the codebase as `self.AMPHandler.tokens.<Field>` (e.g. `AMPUser`, `AMPPassword`, `AMPurl`, `AMPAuth`, `SteamAPIKey`, `token`).

## Production deployment log (Hetzner, `fullsendhub.de`)

First real-world deployment of this fork, done 2026-08-06/07. Standalone systemd service (not an AMP-managed instance), dedicated non-root Linux user, full feature set (`perms_super()`, no `-whitelist-only`). Layout: `/opt/gatekeeper/app` (this repo, `git pull`-updated), `/opt/gatekeeper/venv` (deliberately outside the systemd unit's `ReadWritePaths`, so the running service can never write its own dependencies — see `ExecStart`/hardening directives in `gatekeeper.service`), secrets in `/opt/gatekeeper/gatekeeper.env` (systemd `EnvironmentFile=`, `chmod 600 root:root`). Server runs **Python 3.13**, not the 3.11 the README/setup assumed — that mismatch, plus the target AMP install being a notably newer/updated CubeCoders build, is the root cause behind nearly every fix below. AMP account: `Gatekeeper-Bot`. First discovered instance: `Minecraft-test01`.

### Fixes made getting from "won't even `pip install`" to a working AMP bootstrap
All in `requirements.txt` / `AMP.py` / `logger.py` / `amp_permissions.py`, one commit each (`git log a8f95dd..69e53bd`):
1. **`requirements.txt` couldn't resolve on Python 3.13**: `certifi` too old for the `requests` pin; `aiohttp==3.7.4.post0` predates Python 3.11+ wheels entirely; `multidict==6.0.4` has no cp313 wheel. Bumped all three plus the new transitive deps `aiohttp` 3.10+ pulls in (`aiohappyeyeballs`, `aiosignal`, `frozenlist`), and `typing_extensions` (a transitive floor from `aiosignal`). Verify any future dependency bump the same way: `pip install --dry-run -r requirements.txt` against a real Python 3.13 venv, not just metadata reading.
2. **`haggis.logs.add_logging_level()` crashed on Python 3.13**: it calls the private `logging._acquireLock()`/`_releaseLock()`, which CPython removed in 3.13 (the underlying `logging._lock` is still there). No haggis release fixes this (checked latest, 0.14.1). Fix is a small shim at the top of `logger.py` that backfills those two names before `haggis` is imported.
3. **AMP rejected objectively-correct credentials** (`Core/Login` returning `{'result': 30, 'success': False}` with no reason) because of the exact HTTP request shape — found by capturing the AMP web GUI's real login request via browser DevTools ("Copy as cURL") and diffing against what `AMP.py` sent. Two mismatches, both now in `self.AMPheader` / `CallAPI()`: AMP expects `Content-Type: application/x-www-form-urlencoded; charset=UTF-8` for its JSON body (not `application/json` — a long-standing AMP/jQuery quirk) and `X-Requested-With: XMLHttpRequest`; `CallAPI()` now also always includes the `SESSIONID` key (as `""` pre-login) instead of omitting it. **If AMP ever rejects a request with a generic reason-less failure again, capture the browser's real request first — don't guess at headers.**
4. **Real crash bug, unrelated to this deployment**: `check_GatekeeperRole_Permissions()` referenced `self.Port` when logging a missing-permission warning, but the main instance (`InstanceID == 0`) has no `Port` attribute — `AttributeError` killed the whole AMP Handler thread. Fixed by mirroring the existing `APIModule == "AMP"` branch that `check_SessionPermissions()` already had.
5. **4 stale/renamed permission nodes in `amp_permissions.py::perms_super()`**: `LocalFileBackup.*` (a real grant — losing it costs the `/server backup` functionality until a modern equivalent node name is found) and three now-nonexistent exclusion nodes (`-Settings.GSMyAdmin.*`, `-Settings.LocalFileBackupPlugin.*`, `-ADS.InstanceManagement.Convert` — harmless to drop, nothing to exclude if the node doesn't exist). Confirmed against a live dump of `Core/GetPermissionsSpec` (this AMP build reports 247 real nodes under top-level categories `ADS`/`Core`/`FileManager`/`Instances`/`Settings`/`Store` — notably **no `LocalFileBackup` category at all anymore**). Every other entry in `perms_super()` checked out fine.
6. **`discord.py==2.4.0` + Python 3.13**: `discord.player` imports the stdlib `audioop` module, which Python 3.13 removed (PEP 594). `discord.py` 2.5.0+ handles this itself via a conditional `audioop-lts` dependency; added the same thing (`audioop-lts==0.2.2; python_version >= "3.13"`) to `requirements.txt` rather than bumping `discord.py` itself (that's flagged as a separate, deliberately-untested upgrade — 2.4.0 → 2.7.x has possible breaking API changes).
7. Added raw-response logging to `AMPInstance.Login()`'s and `setAMPRolePermissions()`'s failure paths (they previously logged only "failed", no reason) — this is what made fixes #3 and #5 possible instead of guessing blind. Worth keeping/extending this pattern anywhere else in `AMP.py` that swallows the API response on failure.

### Resolved this session (2026-08-09)
- **Root cause of "bot can't correctly set up its role when given Super Admin" found and fixed**: `setup_AMPbotrole()` called `setAMPUserRoleMembership(...)` to join the bot's own account to the brand-new, still-empty `Gatekeeper` role **before** `setup_Gatekeeper_Permissions()` had set a single permission on it. AMP resolves a user's effective permissions as the union of every role they're a member of, with **deny always beating allow** (confirmed via the AMP GUI's own role-membership help text) — so joining an unconfigured role while also being Super Admin cancelled out the Super Admin grant mid-setup, and every subsequent `Core/SetAMPRolePermission` call failed with `"You cannot assign a permission (X) to a role/user that you yourself do not have."`. Confirmed this was a genuine AMP-side effect, not a request-shape issue: the exact same failure reproduced when manually testing in the AMP GUI itself while logged in as the `Gatekeeper-Bot` account (as opposed to the human's own separate admin account, which worked fine and was the initial red herring that looked like a code bug). **Fix**: reordered `setup_AMPbotrole()` in `AMP.py` to call `setup_Gatekeeper_Permissions()` first and only join the role membership afterward, once the role is fully configured. **Confirmed working end-to-end via a live fresh-bootstrap restart** (Super Admin re-granted, `Gatekeeper` role deleted first): the full ~40-node permission loop completed with no `"you cannot assign a permission you yourself do not have"` errors, followed by a normal self-downgrade and clean startup.
- Also added, as part of the same investigation (kept even though the above was the real root cause, since both are independently correct): `AMPInstance.CallAPI()` now also sends `Authorization: Bearer <SessionID>` on every authenticated call, matching what the browser's AMP web client sends in addition to the existing `SESSIONID` body field (found via the same DevTools-diff methodology as fix #3 above).
- **`Core.UserManagement.ViewUserInfo` self-check false-negative — was escalating to a hard crash, now guarded and confirmed fixed**: restarting past the main-instance bootstrap reached `Minecraft-test01`'s per-instance (ADS delegate) session, where `check_GatekeeperRole_Permissions()`'s self-lookup (`Core/GetAMPUserInfo`) got rejected with `Unauthorized Access` — even though `check_SessionPermissions()` had *just* confirmed that exact same session held every node in `self.perms` (including this one) via the node-based `CurrentSessionHasPermission` check moments earlier. `getAMPUserID()` then indexed the `False` result (`result["ID"]`), throwing an unhandled `TypeError` that killed the whole AMP Handler thread. Root cause still unconfirmed (likely: `Core/GetAMPUserInfo`, an AMP-wide user-info lookup, simply isn't permitted from a per-instance delegate session in this AMP build regardless of the node's grant status), but the crash itself is fixed: `check_GatekeeperRole_Permissions()` and `getAMPUserID()` in `AMP.py` now check `isinstance(result, dict)` before indexing; for `InstanceID != 0` a rejected self-lookup logs a warning and returns `True` (session permissions were already independently verified), while `InstanceID == 0` still logs `critical` and returns `False` (bootstrap-critical, unchanged strictness). Confirmed via live restart: no crash, warning logged as expected, bot proceeds to a working Discord connection.
- **AMP "only reachable via public domain, not loopback" — was a false lead, not a real AMP restriction**: originally documented as `GATEKEEPER_AMP_URL` needing `https://amp.fullsendhub.de` because direct loopback got a generic reason-less login rejection. Re-tested from scratch with a small script that logs into `Core/Login` directly (bypassing the app) against three targets: the public domain, loopback directly, and loopback with a spoofed `Host: amp.fullsendhub.de` header — **all three succeeded** (`"success":true`) once the exact `GATEKEEPER_AMP_USER`/`GATEKEEPER_AMP_PASSWORD` from `/opt/gatekeeper/gatekeeper.env` were used verbatim (the original curl-based test that seemed to show loopback failing had bad/mistyped credentials baked into the command, not an AMP-side host check — 2FA was also ruled out, `IsTwoFactorEnabled` is `false` on this account). AMP's "Approved Reverse Proxy Hosts" setting already listed `127.0.0.1`, which was also a red herring — never the actual blocker. **Fix applied**: `GATEKEEPER_AMP_URL` in `/opt/gatekeeper/gatekeeper.env` switched to `http://127.0.0.1:8080`, service restarted, confirmed working end-to-end. Verified `AMP_Linux_x86_64`'s webserver is bound to `127.0.0.1:8080` only (`ss -tlnp`), not `0.0.0.0`, so this doesn't newly expose anything — it just removes the round trip out to the public internet and back for every single AMP API call, on top of the `requests.Session()` reuse fix. Security effect is minor/secondary (removes reliance on public DNS/reverse-proxy for credential-bearing internal traffic); the previous public-domain path was already TLS to a trusted domain and wasn't actually insecure — this change is primarily a performance win.
- ~~**`CallAPI()` in `AMP.py` opens a brand-new `requests.post()` per call — no connection reuse.**~~ **Implemented**: `AMPHandler` now owns a single `self.http_session = requests.Session()` (created in `AMP_Handler.py::AMPHandler.__init__`), and `AMPInstance.CallAPI()` calls `self.AMPHandler.http_session.post(...)` instead of the module-level `requests.post(...)`. One session is shared across the main instance and every per-server `AMPInstance` since they all talk to the same AMP host (`self.url` is always built from the same `AMPHandler.tokens.AMPurl`, with per-instance/per-server routing only in the URL path) — so it pools TCP/TLS connections across all of them instead of paying a fresh handshake on every call. Combined with the loopback switch above, first-boot bootstrap should now be meaningfully faster than the original "minutes instead of seconds" — not yet precisely re-timed.
- `perms_super()`/`perms_whitelist_only()` reconciled against a full live `Core/GetPermissionsSpec` dump: excluded several nodes granted via wildcard but unused by any code path (`Store.*`, `Core.UserManagement.AccessExternalPermissions`/`ViewActiveSessions`, `ADS.DatastoreManagement.*`, four new `ADS.InstanceManagement` bulk-admin nodes added since the list was first written, and the entire unused `Settings.*` category).
